# 饭搭子模块审查报告

> 审查范围：`static/js/buddy.js`、`services/social.py`、`services/api_v1.py`、`services/auth.py`、`services/db.py`、`templates/index.html`、`templates/invite.html`
> 审查方式：代码走查 + 内存库实证（抽样 300 次）

---

## 一、结论摘要

| 级别 | 数量 | 核心影响 |
|---|---|---|
| **P0 严重** | 4 | 抽搭子算法 4 个权重里有 2 个永久失效；邀请来的搭子等同随机 |
| **P1 重要** | 6 | 无法编辑、无法撤销邀请、会话过期不恢复、并发竞态、数据被覆盖 |
| **P2 体验** | 7 | 文案误导、静默兜底、闭环缺失 |
| **P3 轻微** | 6 | 死代码、无分页、无外键 |

**最关键的发现**：抽搭子号称「距离 40% · 口味 25% · 预算 20% · 久未见面 10% · 随机 5%」，但**距离和久未见面两项恒为中性 0.5**，实际只有口味和预算在起作用。邀请来的搭子因为没有任何信息，抽中概率仍高达约 30%。

## 二、P0 严重问题（核心功能失效）

### 2.1 搭子「常出没商圈」填了完全不生效

**现象**：添加搭子时输入「望京（用于算距离）」，但抽搭子时距离权重没有任何作用。

**根因**：
- 前端 `buddy.js:326-331` `create()` 只传 `{name, area, budget, cuisines}`，**没有把 area 转成经纬度**；
- 后端 `social.py:106-107` `create_buddy` 的 `lat/lng` 取自 payload，前端不传 → `None`；
- `social.py:195-199` `score_buddy`：`buddy.lat/lng` 为 None 时 `proximity = 0.5`（固定中性）。

**实证**：
```
[小明] lat/lng = None None | area = '望京' | last_met = None
[拆解] 小明 {proximity: 0.5, cuisine: 1.0, budget: 1.0, recency: 0.5}
```

**影响**：距离权重（40%，最大权重）永久失效。UI 文案「用于算距离」是**虚假承诺**。

**修复建议**：
- 前端 `openAdd` 保存前调用 `API.geocode(area)` 换坐标，随 `create` 一并提交 `lat/lng`；
- 或后端 `create_buddy` 内部对 `area` 做地理编码兜底（但会拖慢接口，建议前端做，失败时允许为空）；
- 已存在的旧搭子需要一次性补坐标（可加迁移脚本或编辑时补）。

---

### 2.2 「久未见面」权重永久失效

**现象**：抽搭子结果永远不显示「很久没一起吃了」这一条推荐理由。

**根因**：
- `buddies.last_met` 字段存在（`db.py:53`），`update_buddy` 也支持 `lastMet`（`social.py:154-159`）；
- 但**前端没有任何入口**更新它（`buddy.js` 全文无 `lastMet` 调用）；
- `social.py:207-213` `recency` 在 `last_met` 为空时固定 0.5。

**实证**：`recency: 0.5`（所有搭子）。

**影响**：久未见面权重（10%）永久失效，「该约谁了」这个核心价值无法体现。

**修复建议**：
- 抽中搭子后的结果弹层增加「这次就约 TA」按钮，点击 `PATCH /api/buddies/<id>` 更新 `lastMet = today`；
- 或在搭子列表每行加「记一次见面」快捷操作。

---

### 2.3 邀请来的搭子几乎无信息，抽中概率却接近 30%

**现象**：通过邀请链接互加的搭子，抽签时和「信息完整的搭子」概率差距很小。

**根因**：`social.py:332-338` `_upsert_mutual_buddy` 插入时：
- `lat/lng` 不传 → None（距离失效）
- `cuisines` 硬编码 `'[]'`（口味失效，`affinity` 恒 0.4）
- `budget` 不传 → None（预算失效）
- `last_met` 不传 → None（久未见面失效）

**实证**（300 次抽样）：
```
分布：小红 91 次（30.3%）、小明 209 次（69.7%）
[小红] {proximity: 0.5, cuisine: 0.4, budget: 0.5, recency: 0.5}  ← 全部中性
```

**影响**：一个完全没信息的搭子，抽中概率约 30%，稀释了真实偏好匹配的价值。

**修复建议**：
- 邀请接受后引导补充标签（口味/预算/区域），未补充的搭子在抽取时降低权重（例如 `weight *= 0.6` 作为「信息不完整惩罚」）；
- 或在 UI 上标注「信息不完整，去补充」并给出编辑入口（依赖 2.4/3.1）。

### 2.4 同名搭子被邀请覆盖，区域数据被清空

**现象**：你手工添加过「阿强」并填了区域/口味/预算，之后阿强本人接受邀请，你目录里的「阿强」区域变成空白。

**根因**：`social.py:333-338`
```sql
INSERT INTO buddies (...) VALUES (...)
ON CONFLICT(owner_id, name) DO UPDATE SET area = excluded.area, source = excluded.source
```
`excluded.area` 来自 `inviter["city"] or ""`（通常为空），直接把手工填的区域覆盖为空，`source` 也被改成 `invite`。

**实证**：
```
[同名覆盖] 覆盖前 area='国贸' → 覆盖后 area=''  | cuisines 保留 | budget 保留 | source=invite
```

**影响**：手工数据丢失（区域），且搭子被错误标记为「邀请加入」。

**修复建议**：
```sql
ON CONFLICT(owner_id, name) DO UPDATE SET
  area   = CASE WHEN excluded.area != '' THEN excluded.area ELSE buddies.area END,
  source = CASE WHEN buddies.source = 'manual' THEN 'manual' ELSE excluded.source END
```
即「非空才覆盖、手工来源不被邀请降级」。

## 三、P1 重要问题

### 3.1 搭子无法编辑（只能删除重建）

- 后端已实现 `PATCH /api/buddies/<id>`（`api_v1.py:128-132`）与 `update_buddy`（`social.py:128-169`），支持改昵称/区域/坐标/口味/预算/见面时间；
- **前端无任何编辑入口**（`index.html:408-418` 列表只有「添加」「发邀请」；`renderList` 每行只有骰子、删除两个按钮）；
- `api.js` 的 `updateBuddy` 已定义但**从未被调用**（死代码）。

**影响**：改个预算要删了重加，丢失 `created_at` 与历史关联；也是 2.2/2.3 修复的前置依赖。

---

### 3.2 邀请无法撤销、无「我发出的邀请」列表

- 后端已有 `DELETE /api/invites/<token>`（`api_v1.py:173-178`）与 `revoke_invite`；
- 前端 `showInvite`（`buddy.js:395-442`）只有「复制链接」「分享给朋友」「知道了」，**没有撤销**；
- `api.js` 也没有 `revokeInvite` 方法。

**影响**：邀请链接发错人 / 发到群里，7 天内无法收回，任何人拿到即可成为搭子。

---

### 3.3 抽搭子使用了过期的「当前店铺」

**现象**：在首页抽搭子，用的可能是你几分钟前在详情页看过的某家店的位置、菜系、预算。

**根因**：
- `buddy.js:456` `const item = App.state.current;`；
- `App.state.current` 只在 `detail.js:27/75` 赋值，**离开详情页从不清空**（全仓库无 `App.state.current = null`）；
- 一旦 `item` 存在，`payload` 就用 `item.lat/lng/cuisine/avgPrice` 而不是用户当前位置。

**影响**：抽取依据与用户预期不符；如果上次看的店在 5km 外，距离权重会算错。

**修复建议**：仅在详情页上下文（`App.state.page === 1`）使用 `current`，否则用 `App.state.location`。

---

### 3.4 接受邀请后，对方名称可能是「本机用户」

**根因**：
- `auth.py:62` `upsert_device_user` 未填昵称时默认 `"本机用户"`；
- `social.py:319` `invitee_name = (user["nickname"] or "饭搭子")[:20]` → 拿到的是「本机用户」。

**影响**：邀请方的搭子列表里出现一个叫「本机用户」的搭子，无法辨认是谁。

**修复建议**：接受邀请页（`invite.html`）已要求填昵称（`#nickname` 必填），确保 `auth/device` 带上昵称；同时在 `accept_invite` 侧对 `"本机用户"` 做兜底（例如改用 `邀请 + 时间`）。

---

### 3.5 会话过期后不会自动恢复

**根因**：`buddy.js:53-73` `ensureSession()` 在 `this.ready === true` 时直接返回 true，永不校验会话是否仍有效。会话 30 天过期后（`auth.py:26`），所有 `/api/buddies` 请求返回 401，前端只 toast 错误，不会重新 `authDevice`。

**影响**：长期用户某天打开应用，饭搭子/骰子/邀请全部报错，需手动刷新页面才能恢复（刷新后 `ready=false` 才会重建）。

**修复建议**：捕获 401 时把 `ready = false` 并重试一次 `ensureSession()`。

---

### 3.6 接受邀请存在并发竞态

**根因**：`social.py:304-329` `accept_invite` 是 check-then-act：
```python
row = SELECT ... WHERE token=?         # 读
if row["status"] != "pending": 409     # 判断
...
UPDATE invites SET status='accepted'   # 写（没有 WHERE status='pending'）
```
两个不同用户同时用同一 token 接受，可能都通过判断，都写入搭子。

**影响**：邀请方目录里多出一个搭子（`ON CONFLICT` 幂等，不会重复行，但会多一个人）。

**修复建议**：
```python
cur = db.execute("UPDATE invites SET status='accepted', accepted_by=? WHERE token=? AND status='pending'", ...)
if cur.rowcount == 0: raise ApiError("invite_used", ...)
# 再写搭子
```
