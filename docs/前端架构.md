# 前端架构与状态说明

面向维护者：说明 22 个 JS 模块的职责边界、状态归属与一次典型渲染的数据流，以及性能与导航改造的取舍。

---

## 一、模块职责

| 模块 | 职责 | 依赖 |
|---|---|---|
| `telemetry.js` | 前端错误上报：错误/拒绝/资源失败，去重限量 | 无 |

| `bubbles.js` | 评价泡泡动画、点击展开、暂停/恢复 | util |
| `filters.js` | 五步筛选状态、弹层、已选条件、过滤函数 | App.changeDistance |
| `feed.js` | 双列瀑布流、分页、DOM 复用、口味微调 | Filters、Store |
| `detail.js` | 详情渲染、画廊、打卡、出行方式弹层 | api、store、bubbles |
| `nav.js` | 路线请求、地图渲染、原生导航跳转 | api、map |
| `play.js` | 游玩点位、顺路度卡片、地图 | api、map |
| `checkin.js` | 统计、日期分组、导出/导入 | store |

加载顺序即上表顺序（`app.js` 最后），所有模块通过 `window.*` 暴露单例，无打包步骤。

## 二、状态归属（单一来源）

| 状态 | 归属 | 说明 |
|---|---|---|
| 当前页 / 当前商家 / 出行方式 / 已拉取半径 | `App.state` | 运行时状态，不持久化 |
| 五步筛选条件 + 只看营业中 | `Filters.state` | 仅会话内有效；营业时间缺失按未知放行 |
| 饭后可用时间 | `Play.budget` | 0 表示不限，仅前端过滤 |
| 周末子模式 | `App.state.weekendSubmode` | solo / group，持久化到 Store.prefs |
| 商家列表（原始） | `Feed.items` | 来自 `/api/restaurants` |
| 商家列表（筛选 + 口味排序后） | `Feed.filtered` | **派生状态**，只在 `Feed.render()` 里重算 |
| 打卡记录 / 周末手动开关 / 子模式 / 手动位置 | `Store.data` | 持久化到 localStorage |
| 详情页异步补齐的数据 | `Detail.data` | 与列表项合并，不写回 Feed |
| 导航路线 / 游玩点位 | `App.state.route`、`Play.data` | 页面级缓存，切页不重复请求 |
| 会话用户 | `App.state.user` | 匿名设备换取，`Buddy.ready` 标记是否可用 |
| 雷达开关 | `App.state.radarOpen` | 全屏浮层，返回键先关雷达，`Radar.render` 随筛选同步 |
| 云登录态 | `Cloud.client` / 会话 | 打卡上云；未登录仍存本机，`Checkin.refreshCloudState` 刷新状态行 |
| 搭子目录 / 选中搭子 | `Buddy.items`、`Buddy.selectedId` | 服务端为唯一来源，开浮层时刷新 |
| 团购结果 | `Deals.cache` | 按门店缓存，避免重复请求 |

约定：

- **派生数据不缓存两份**：随机抽店直接复用 `Feed.filtered`，不再单独过滤一次；
- **页面级数据不下沉全局**：详情评价、路线、游玩点位各自持有，避免全局状态膨胀；
- **写入只经 Store**：任何持久化字段都走 `Store.save()`，不在业务代码里直接碰 localStorage。

## 三、一次筛选的数据流

```
用户点菜系 / 拖价格 / 选距离
        │
        ▼
Filters.renderCuisine / renderFilterChips / renderCond   ← 只更新筛选 UI
        │
        ▼
App.applyFilters（60ms 防抖）
        │
        ▼
Feed.render()
  ├─ 收集旧卡片 DOM（Map<id, node>）
  ├─ 读一次列宽
  ├─ Filters.apply(items)          ← 纯函数过滤
  ├─ Feed.personalize(list)        ← 按打卡菜系对距离做 ≤35% 修正
  ├─ 清空两列，按 id 复用卡片或新建
  └─ 更新“共 N 家”计数
```

距离档位是唯一会触发网络请求的筛选：

- 新档位 ≤ 已拉取半径 → 本地过滤；
- 超出已拉取半径 → `App.reloadData()`，并 abort 上一个请求，旧响应按序号丢弃。

## 四、本轮性能改造

| 改造 | 位置 | 收益 |
|---|---|---|
| 图片两档（480w / 1080w）+ `srcset` | `static/img`、`util.srcset` | 8.49MB → 1.41MB（-83%），首屏 4 张图 3.7MB → 96KB |
| 列表用缩略图，详情/抽奖用大图 | `feed.js`、`detail.js`、`draw.js`、`checkin.js` | 列表解码量下降约 90% |
| 首图 `fetchpriority=high`、前两张 eager | `feed.js`、`detail.js` | 改善 LCP，避免懒加载拖慢首屏 |
| 卡片 DOM 复用（按 id + 数据签名） | `feed.js` | 切筛选不重建节点、不重新下载图片、不重放入场动画 |
| 列宽只读一次 | `feed.js` | 消除循环内强制回流 |
| 请求可取消 + 序号防乱序 | `app.js`、`api.js`、`detail.js` | 快速切筛选/切商家时，慢响应不再覆盖新结果 |
| Pager 用像素位移替代 `calc(%)` | `pager.js` | 拖动时减少样式解析与重算 |
| 移除未使用的 Bootstrap CSS | `templates/*.html` | 减少 233KB 传输，消除同名类冲突 |
| 启动时合并 CSS/JS | `services/bundles.py` | 首屏资源请求 18 → 2，gzip 后 CSS 11KB / JS 43.9KB |
| WebP + `<picture>` 回退 | `tools/img_webp.js`、`util.webpSource` | 缩略图 -32%，大图 -35%，旧浏览器回退 JPEG |
| 泡泡只在本页可见时运行 | `bubbles.js`、`app.js` | 切页/后台标签页不再占用 rAF |
| 地图标签碰撞避让 | `map.js` | 标签按候选位置择优选点，游玩页不再互相遮挡 |
| 评价生成结果缓存 | `provider_demo.py` | 单次搜索不再重复生成 16×6 条评价 |
| 页面进入守卫 | `pager.js:go` | 无选中商家时不会滑出空白详情页 |
| 浏览器历史栈 | `app.js:bindHistory` | 返回键逐级返回；浮层打开时先关浮层；预留哨兵记录避免直接退出站点 |
| 弹层焦点陷阱 | `util.js:openSheet` | Tab 在弹层内循环，关闭后焦点归位 |
| Tab 语义化 | `index.html`、`app.js:updateChrome` | `role=tablist/tab` + `aria-selected` 随页面同步 |
| 营业状态统一解析 | `util.openState` | 支持「次日 02:00」跨夜，列表/详情共用 |
| 分享链接直达 | `app.js:openSharedStore` | `/?store=<id>` 打开即进详情 |

未采用的手段及原因：

- **不做虚拟列表**：首屏 12 张、单页最多 16 家，DOM 规模小，虚拟列表反而增加复杂度；
- **不引入前端构建链**：仍保留独立源文件，`services/bundles.py` 在进程启动时按依赖顺序拼接，既减少请求，又不增加 npm/打包配置；上生产建议由 Nginx 开 HTTP/2 + brotli；
- **不做服务端 POI 缓存**：PRD 要求实时拉取；仅做单请求内去重与评价语料缓存。

## 五、后端状态与错误边界

- `DataService` 无状态（除 demo 语料缓存），可安全用于多线程 dev server；
- `Crawler.STATS`、`HostLimiter`、`RateLimiter` 均带锁，计数不跨进程；
- 所有 provider 失败统一抛 `ProviderError`，由 `DataService` 决定切源/扩半径；
- 对外只抛 `FriendlyError`（message/hint/code），堆栈仅进日志；
- HTTP 状态码：参数错 400、找不到 404、限流 429、未捕获 500，前端一律读 JSON。

## 六、扩展指引

**新增菜系**：在 `filters.js` 的 `CUISINES` 与 `provider_amap.CUISINE_RULES` 各加一条；`ranker.PER_CAPITA_TIERS` 判断是否需要归入饮品。

**新增筛选步骤**：在 `Filters.state` 加字段 → `renderFilterChips` 加一个 chip → `openPanel` 加分支 → `Filters.apply` 加判断 → `renderCond` 加可删除项。顺序需与 PRD 一致。

**接入新数据源**：实现 `BaseProvider` 的 `search_nearby/place_detail/route/geocode`，在 `crawler.SOURCES` 注册来源与限流，在 `DataService.order` 中排序即可；前端无感。

**替换地图**：`MapView.render(el, options)` 是唯一入口，新增分支返回 `{zoom}` 控制句柄即可。
