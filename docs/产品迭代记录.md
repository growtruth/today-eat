## 第三轮：决策可信度与轻量传播（2026-10-26）

### 一、评估方法

每条需求按四个维度打分（1–5），再结合成本做取舍：

- **用户价值**：是否直接减少「选错 / 选不出」；
- **覆盖范围**：受影响用户比例；
- **实现成本**：改动文件数、是否需要新数据；
- **风险**：数据缺失时是否产生新的错误判断。

原则：优先做「用现有数据就能变准」和「不需要用户学习」的改动，暂缓需要新数据源或改变产品边界的需求。

### 二、候选清单与结论

| 候选需求 | 价值 | 覆盖 | 成本 | 风险 | 结论 |
|---|---|---|---|---|---|
| 营业状态可信化（跨夜解析 + 列表标记 + 只看营业中） | 5 | 5 | 2 | 低（缺失按未知放行） | **本轮做** |
| 饭后游玩按可用时间筛选 | 4 | 3 | 2 | 低 | **本轮做** |
| 抽店结果可分享，链接直达该店 | 3 | 3 | 2 | 低 | **本轮做** |
| 首屏手势提示（左右滑 / 摇一摇） | 3 | 4 | 1 | 低 | **本轮做** |
| 打卡时记录实际人均与是否再来 | 4 | 3 | 3 | 中（增加打卡摩擦） | 下一轮 |
| 场景化入口（一人食 / 30 元吃饱 / 深夜） | 4 | 4 | 3 | 中（与现有筛选重叠、首页变挤） | 下一轮 |
| 收藏 / 心愿单 | 4 | 4 | 3 | 高（与 PRD「不做收藏」冲突） | 不做，需产品边界确认 |
| 多平台评价原文聚合 | 5 | 5 | 5 | 高（平台授权、合规） | 不做，走官方授权 |

### 三、本轮落地

#### 1. 营业状态可信化

**问题**：列表不显示营业状态；详情页解析不支持「次日 02:00」，16 家里 4 家深夜店永远不显示状态；用户可能在上午 10 点被推荐一家 16 点才开门的店。

**做法**：

- `util.openState()` 统一解析 `11:00` 与 `次日 02:00`，支持跨夜（22:00–02:00）；
- 列表卡片显示「已打烊」角标并降低饱和度；
- 新增「营业中」筛选（条件条可移除）；
- **数据缺失时不误判**：没有营业时间的门店视为「未知」，筛选时放行。

**取舍**：没有默认开启「只看营业中」，因为真实数据源不一定返回营业时间，默认过滤会误伤；先让用户按需开启。

#### 2. 饭后游玩按可用时间筛选

**问题**：8 个点位一次全铺开，用户不知道自己还有多久，容易选到「还要再走 20 分钟」的地方。

**做法**：新增 不限 / 30 分钟内 / 1 小时内 / 2 小时内 四档，按步行时间过滤卡片与地图点位；无结果时提示放宽。

**取舍**：不改后端接口，使用已返回的 `walkMinutes`；时间档位固定四档，避免变成滑块增加操作成本。

#### 3. 抽店结果可分享

**问题**：抽到店之后只能自己看，无法把结果发给同行的人；这是「一起决定」场景的断点。

**做法**：结果卡增加「分享给朋友一起决定」，生成文案 + `?store=<id>` 链接；有系统分享用系统分享，否则复制到剪贴板。链接打开后直接进入该店详情。

**取舍**：不做分享海报图片，避免引入 Canvas 绘制与字体问题；文字 + 链接已满足群聊决策。

#### 4. 首屏手势提示

**问题**：新用户不知道可以左右滑看详情、摇一摇换一家，核心交互靠猜。

**做法**：首次加载后浮出提示条，6 秒自动收起，可点「知道了」；`localStorage` 记录已读，只出现一次。

**取舍**：不做多步引导遮罩，避免打断首屏浏览；提示条只出现一次，不重复打扰。

### 四、验证

| 项目 | 结果 |
|---|---|
| 跨夜营业判定 | 凌晨 1 点判为营业，中午 12 点判为打烊 |
| 缺少营业时间 | `known=false`，不会被当作打烊过滤 |
| 营业中筛选 | 开启后进入条件条，可单条移除 |
| 时间预算 | 10 分钟预算下点位数量下降且全部 ≤10 分钟 |
| 分享链接 | `/?store=demo-001` 直接打开对应门店详情 |
| 自动化 | 规则 66 项、后端 59 项、浏览器 88 项全通过 |

### 五、建议观测指标（尚未埋点）

当前项目没有前端埋点，以下指标需要接入统计后才能验证：

- 抽店结果 → 详情页打开率（衡量随机结果是否有吸引力）；
- 分享按钮点击率、分享链接打开率（衡量传播）；
- 「营业中」筛选使用率、开启后结果数变化；
- 时间预算档位分布（判断默认档位是否合理）；
- 空结果率与清空筛选点击率（衡量筛选是否过严）。

### 六、下一轮候选

1. 打卡记录「实际人均 + 是否再来」，用于修正推荐与统计（需评估打卡摩擦）；

## 第四轮：饭搭子可信度修复（2026-10-29）

### 一、发现

对饭搭子模块做了一次完整审查（`docs/饭搭子模块审查.md`），用内存库抽样 300 次复现，确认 **23 个问题**：

- 抽搭子 UI 写着「距离 40%」，但 `proximity` 与 `recency` 恒为中性 0.5——真正生效的只有口味（25%）和预算（20%）；
- 邀请来的搭子没有任何资料，抽中率却接近 30%，把偏好匹配的价值稀释掉了；
- 手工填的商圈被同名邀请覆盖为空，`source` 也被改成「邀请加入」。

### 二、取舍

| 候选 | 价值 | 成本 | 结论 |
|---|---|---|---|
| 商圈→坐标（前端地理编码 + 城市限定 + 150km 校验） | 高（救回 40% 权重） | 中 | 做 |
| 见面闭环（抽取后记一次约饭） | 高（救回 10% 权重） | 低 | 做 |
| 资料完整度降权（0.6+0.4×完整度） | 高（修正概率失真） | 低 | 做 |
| 同名保护 / 编辑 / 撤销 / 并发原子化 / 会话自愈 | 高（数据安全与可管理） | 中 | 做 |
| 搭子列表分页、骰子历史分页 | 低（数据量小） | 低 | 暂缓 |

**原则延续**：不新增数据源，先把现有字段用准；数据缺失按「未知」处理并显式降权，而不是假装中性。

### 三、落地

- 后端：`profile_completeness` + 权重折算、`_upsert_mutual_buddy` 保住手工资料、`accept_invite` 原子占用、`create_invite` 复用 pending、`_display_name` 兜底、新增 `PATCH /api/me`；
- 前端：新增/编辑共用表单、保存前地理编码、`backfillCoords` 补旧数据、`markMet` 记约饭、邀请撤销、`Buddy.call()` 401 自愈、详情页上下文作用域修正、骰子不再静默换人。

|---|---|
| 规则测试 | 66 项全过 |
| 后端测试 | 74 项全过（新增 15 项针对本轮修复） |
| 浏览器端到端 | 88 项全过 |
| 真实高德 | 望京 → `39.996171, 116.470293`；国贸（限北京市）→ `39.90986, 116.45885` |
| 降权效果 | 500 次抽样，空资料搭子占比 < 25%（修复前约 30%） |

## 第六轮：修复线上写接口全部 403（2026-10-30）

### 一、问题

线上「饭搭子」长期不可用：打开面板提示「搭子服务没连上」，添加/抽签/邀请/骰子全部失败。

### 二、定位

浏览器实测报错 `跨站请求被拒绝`（`code=cross_origin`）。抓包对比：

| 请求 | 结果 |
|---|---|
| curl 无 `Origin` | 200 |
| curl 带**正确公网** `Origin` | **403** |
| curl 带恶意 `Origin` | 403 |

代码在 `services/web_security.py`：`netloc != request.host`。
平台网关会把 `Host` 改写成内网地址，浏览器 `Origin` 是公网域名，两者永远不相等 —— 于是
**所有 POST/PATCH/DELETE 都被误判为跨站**，读接口（GET）不受影响，所以只有「登录/保存/邀请/骰子」坏。

### 三、修复

- `_candidate_hosts()`：`Host` + `X-Forwarded-Host` + 新增配置 `PUBLIC_HOSTS`（逗号分隔，可选）；
- `_same_origin()`：先比对候选主机名，再以浏览器自带的 `Sec-Fetch-Site`（`same-origin`/`none`）兜底；
- 真正的跨站 `Origin`（如 `evil.example.com`）仍然 403，防护没有被削弱。

### 四、验证

| 项 | 结果 |
|---|---|
| 本地代理场景（公网 Origin + 内网 Host） | 200 |
| 本地恶意 Origin | 403 |
| 线上浏览器：面板 | 正常加载，无错误 |
| 线上浏览器：新建搭子 | 成功，望京坐标 39.996171,116.470293 |
| 线上浏览器：抽搭子 | 「陪你吃的是 TA」，两条操作按钮正常 |
| 线上浏览器：邀请 | 链接带 sharecode，撤销入口正常 |
| 自动化 | rules 66 / backend 85 / e2e 88 |

### 五、经验

部署在反向代理后的应用，任何依赖 `request.host` 的逻辑（同源校验、绝对 URL 拼接、Cookie 域）
都必须同时考虑 `X-Forwarded-Host`，否则本地测试全绿、线上用户全挂。

## 第七轮：微信登录链路修复（2026-10-30）

### 一、问题

搭子面板点「微信登录」没有反应，或登录后仍显示「本机身份」。

### 二、定位（四处独立缺陷叠加）

| # | 问题 | 位置 | 后果 |
|---|---|---|---|
| 1 | 前端读 `user.wechatOpenid`，后端返回的是 `wechat`（布尔） | `buddy.js` `renderProfile` | 登录成功也永远显示「本机身份」「微信登录」 |
| 2 | 授权跳转没带 `sharecode` | `buddy.js` `wechatLogin` | 分享域名下 `/auth/wechat` 直接被门禁挡成 403 |
| 3 | `redirect_uri` 必须手填，且未配置就用内网 host | `wechat.py` | 反向代理下回调地址错误，微信侧回调失败 |
| 4 | 回跳只弹 toast，不刷新身份 | `app.js` `handleWechatResult` | 登录完成后界面不同步，像没生效 |

另：未配置时只用一条 3 秒 toast 提示，用户看不出「缺什么」。

### 三、修复

- `renderProfile` 改用 `user.wechat`，按钮状态与「微信已登录」文案随之正确；
- 授权链接带上 `sharecode`，回跳地址保留查询参数（`_with_query`），失败分支也带 `reason`；
- `wechat.redirect_uri()`：优先 `WECHAT_REDIRECT_URI`，否则按 `X-Forwarded-Host` / `PUBLIC_HOSTS` 自动拼；
  `configured()` 改为只需 AppID + Secret（回调地址可推导）；
- `handleWechatResult`：成功时清空本地会话状态并 `Buddy.refresh()`，失败提示带错误码；
- 未配置时点击弹出说明弹层（缺什么、当前域名为什么不行、本机身份的边界），不再一闪而过；
- `config.py` 新增 `PUBLIC_HOSTS`，`.env` 填入实际对外域名。

### 四、验证

| 项 | 结果 |
|---|---|
| 后端：未配置跳转保留 sharecode | `/?sharecode=SC123&wechat=unconfigured` |
| 后端：回调地址按对外域名推导 | `https://today-eat-47626.app.workbuddy.host/auth/wechat/callback` |
| 后端：state 记录保留分享码 | 通过 |
| 后端：回调失败保留 sharecode | `/?sharecode=SC999&wechat=state_invalid` |
| 前端：未配置点击 | 弹层「微信登录未启用」+ 说明 + 知道了 |
| 前端：字段映射 | `wechat` 字段生效，按钮/文案状态正确 |
| 自动化 | rules 66 / backend 89（新增 4 项）/ e2e 88 |

### 五、限制

当前分享域名 `*.app.workbuddy.host` 无法在公众号后台登记为「网页授权域名」，
微信侧回调也拿不到 `sharecode`，因此**在这台域名上无法完成真实微信授权**。
要启用：自有域名 + 认证服务号，配置 `WECHAT_APP_ID` / `WECHAT_APP_SECRET`（回调地址可留空自动推导）。

## 第八轮：WorkBuddy 账号登录（替代微信服务号，2026-10-30）

### 一、为什么做

微信网页授权要求「认证服务号 + 可登记的网页授权域名」，当前分享域名无法满足。
云服务本身带 OAuth 通道，且就挂在本站域名下，于是把「账号登录」接成正式的身份入口。

### 二、接口事实（实测）

- SDK 把所有云接口挂在 `/.cloud` 下：auth 为 `{CLOUD_ENDPOINT}/.cloud/auth/v1/*`
- 校验会话：`GET /.cloud/auth/v1/user/me`
  - 头：`x-wb-webapp-access-key: <publishableKey>` + `Authorization: Bearer <access_token>`
  - 无 token → `{"code":"UNAUTHENTICATED"}`；假 token → `{"error":"invalid_grant"}`

### 三、实现

**后端**
- `services/cloud_auth.py`：`verify_token()` 服务端核验 token，返回 `{uid,email,name,avatar}`；
  前端传来的 uid 一律不采信（防止伪造身份）。
- `POST /api/auth/cloud`：核验 → 落库 → 建本站会话（Cookie）。
- `services/auth.py` 新增 `upsert_cloud_user()`：
  已有同 uid → 复用；有当前设备会话 → **绑定到该用户**（搭子/打卡数据不丢）；否则新建并按 deviceId 关联。
  昵称只在默认值（本机用户/微信用户等）时覆盖。
- `users` 表新增 `cloud_uid`（唯一索引）/ `cloud_email`，`init_db` 里做幂等迁移。

**前端**
- `Cloud.accessToken()` 取云会话 token；`API.authCloud()` 换本站会话；
- `app.js` 启动时若已有云会话，自动换一次本站会话（`linkCloudAccount`）；
- 搭子面板按钮三态：微信已配置 → 「微信登录」；未配置但云可用 → 「账号登录」；都没有 → 说明弹层；
- 登录态文案区分「账号已登录 / 微信已登录 / 本机身份」。

### 四、验证

| 项 | 结果 |
|---|---|
| 空 token | 400 `invalid_token` |
| 假 token（真实云端） | 401 `cloud_auth_failed`（证明走到了云端） |
| 绑定现有设备用户 | 用户 id 不变，原有搭子仍在 |
| 同账号换设备 | 复用同一 user |
| 线上点击「账号登录」 | 跳转 `www.workbuddy.cn/login/?platform=open-platform-v2...`（正常登录页） |
| 自动化 | rules 66 / backend 98（新增 9 项）/ e2e 88 |

### 五、说明

- 登录完成后回跳 `?provider=workbuddy&code=...`，SDK 换会话，前端再调 `/api/auth/cloud` 落本站会话；
- 账号登录与微信登录可共存：配了服务号优先走微信，否则走账号；
- 本机身份仍然保留，不登录也能用全部功能，只是换设备不同步。
